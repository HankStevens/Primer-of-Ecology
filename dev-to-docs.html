Primer of Ecology · publishing workflow

How your book gets from a draft edit to the live site

A walk-through of every step in your two publish scripts — what each git command actually does, why the branches are shaped the way they are, and why you sometimes got dropped into an editor you didn't ask for.

Repo: HankStevens/Primer-of-Ecology  ·  branches: dev (where you work) and master (what's live)

01 · Mental model

Two branches, one live site

Everything below is really just this picture, worked out in detail. Keep it in your head and the individual git commands stop feeling arbitrary.

The whole system exists to solve one problem: you need somewhere to work on a chapter mid-sentence without the half-finished version going live. dev is that workspace. master is the one branch GitHub Pages actually serves — specifically, the docs/ folder inside it. Nothing you do on dev is visible to a reader until it has gone through one of the two publish paths above.

02 · Vocabulary

Five words worth actually understanding

Most git confusion isn't about your repo — it's that these words get used loosely. Pinned down once, the rest gets much easier to follow.

commit
A saved snapshot of every file in the project, plus a message describing what changed. Not a save of one file — the whole project, as it stood at that moment. Every commit points back to the commit before it, so the full history is a chain.
branch
A name pointing at one commit in that chain. dev and master are two different names pointing at two different (often overlapping) points in the same history. "Switching branches" just moves which chain you're adding new commits to — and rewrites the files on disk to match wherever that name currently points.
merge
Taking the commits that exist on one branch but not another, and folding them in. If the branches haven't diverged, this is trivial (a fast-forward). If both branches gained commits independently — which is normal for you — git has to combine them and creates one new commit to record how. That new commit needs a message, which is the entire reason Vim used to appear.
remote / origin
Your laptop has the whole repo, but so does GitHub's server — that copy is called origin. Committing only changes your local copy. push sends your commits to origin; that's the moment anything becomes visible to GitHub Pages or a collaborator.
working tree
The actual files on disk right now, as opposed to what's committed. "Clean" means the files on disk exactly match the last commit — nothing edited, nothing new. Both of your publish scripts refuse to run on a dirty tree, because switching branches with uncommitted changes sitting around is how work gets lost or tangled into the wrong branch.
03 · This repo, specifically

What dev and master are for here

Generic git advice says "use branches." Yours are shaped around one specific fact: quarto render writes different places depending on a flag, and only one of those places is the live site.

 devmaster
What it's forEvery edit, every draft, every "let me just check this renders"Only ever updated by a publish script
Plain quarto renderGoes to gitignored _book/ — a private preview, invisible to git and GitHubNever run plain here — always with --output-dir docs, deliberately
Commit habitsCommit often, plain git commit is fine — that's a normal editor prompt, not a bugOnly ever committed by a script, with a fixed message
Who reads itNobody but youAnyone at your GitHub Pages URL, via docs/
Why not render straight to docs/ on dev?

Because docs/ is the live site. A render on dev reflects whatever you're mid-edit on — possibly broken, possibly half a chapter. If that ever landed in docs/, it would already be public the moment you committed. Keeping the flag off by default on dev, and only ever adding it deliberately on master inside a script, is what makes that impossible by accident.

04 · Day to day

Editing, with no publishing involved

This is most of your time in the repo, and it's the simplest part — you never leave dev.

  1. Confirm where you are git branch --show-current

    Prints the one branch name you're currently on. A cheap habit before editing, since every step below assumes you're on dev.

  2. Edit, then git commit

    A plain commit with no -m opens your editor so you can write a message by hand. That's expected here — you're not merging anything, just describing your own change.

  3. Preview with quarto render

    No --output-dir flag, so it lands in _book/ and nothing git-tracked changes. Open _book/index.html to eyeball it, or run quarto preview for live reload.

  4. Commit again to snapshot the checkpoint

    Cheap, local, reversible. There's no cost to committing often on dev — nothing becomes public until a publish script runs.

05 · scripts/publish-chapter.sh

Publishing one finished chapter

For an edit contained entirely inside one .qmd file. Run as scripts/publish-chapter.sh 07-direct_comp_mut.qmd from the repo root, while on a clean dev.

  1. Guard checks

    Refuses to continue unless: a filename was given and exists, you're actually on dev, and the working tree is clean. Each check exists to stop a specific accident — wrong branch, uncommitted changes riding along, a typo'd filename.

  2. Checkpoint — does this chapter touch anything shared?

    Shows the chapter's recent commit log and waits for Enter. The single-file pull two steps from now is narrow by design: if this chapter's edits also touched book-refs.bib or _quarto.yml, those changes will not come along, silently. This pause is your one chance to notice and back out.

  3. git checkout master

    Switches branches. Every file on disk now reflects master's last published state, not dev's.

  4. git checkout dev -- chapter.qmd

    Pulls the content of exactly that one file from dev, staged as a change on top of master. Not a merge — no other file moves, no dev history comes along.

  5. quarto render --output-dir docs

    Rebuilds the whole book — this chapter's new content next to master's already-published version of every other chapter, cross-references and all. This is what makes the result the book exactly as it will actually look once live.

  6. Checkpoint — does the diff match what you expect?

    git status and git diff --stat, then wait for Enter. Your last look before anything is permanent; Ctrl-C here backs out cleanly, since nothing has been committed yet.

  7. Commit, then git push origin master

    This is the moment the chapter actually goes live — push is what sends the commit to GitHub.

  8. git checkout dev → git merge master --no-edit

    Brings master's freshly-rendered docs/*.html back onto dev, so dev doesn't show a phantom docs/ diff next time you render there. --no-edit accepts git's automatic merge message instead of opening an editor.

06 · scripts/publish-global.sh

Publishing a change that isn't one chapter

For _quarto.yml, book-refs.bib, a shared script, or more than one chapter at once — anything the single-file trick above would silently leave behind. You commit the change on dev yourself first; the script picks up from there.

  1. Make the change, preview, commit — on dev, by hand

    quarto render (no flag, previews to _book/) → eyeball _book/index.html → git add -A → git commit -m "...". The script assumes this is already done; it refuses to run on a dirty tree.

  2. Run scripts/publish-global.sh

    Same guard checks as the chapter script: clean tree, correct branch.

  3. Checkpoint — last few commits, one look before merging

    Shows git log --oneline -5 and waits. Unlike the chapter script, everything currently on dev is about to move — this is your chance to confirm dev doesn't have some unrelated half-finished thing sitting on it.

  4. git checkout master → git merge dev --no-edit

    A real merge, not a single-file pull — every commit currently on dev moves onto master. This is very likely not a fast-forward, which is exactly why --no-edit matters: without it, git stops here for an editor.

  5. quarto render --output-dir docs

    Full rebuild into the live folder, same as the chapter path.

  6. Checkpoint — diff, then confirm

    git status / git diff --stat, then a prompt for the publish commit message (typed in your terminal, not an editor) before commit and push.

  7. Commit, git push origin master

  8. git checkout dev → git merge master --no-edit

    Same resync as the chapter path, keeping the two branches from drifting apart.

07 · The thing that kept happening

Why you landed in Vim, and what actually fixes it

Not a bug in your repo — a gap in the original commands, now closed in both scripts.

Any git merge between two branches that have each gained commits on their own isn't a fast-forward. Git has to create one new commit to represent the merge, and that commit needs a message — so git opens whatever $EDITOR is configured (Vim, by default on most systems) and waits. This happens even when the merge itself is entirely conflict-free; the prompt is only ever about the message, never about a problem.

The fix is to stop leaving that message unspecified:

CommandWhat happens
git merge devOpens Vim if the merge isn't a fast-forward — the trap.
git merge dev --no-editAccepts git's auto-generated message ("Merge branch 'dev'"). What both scripts now use everywhere.
git merge dev -m "..."Supplies your own message directly, no editor either way.

If you land in Vim anyway

You'll see -- INSERT -- at the bottom if you start typing — that means anything you type is going into the commit message. To get out cleanly:

# press Esc first, always, before any of these
:wq          # save the message as-is and finish the commit
ZZ           # same thing, two keystrokes
:q!          # quit without saving (only if nothing needs keeping)
